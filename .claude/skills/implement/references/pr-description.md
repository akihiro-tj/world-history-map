# PR 説明文の書き方

Step 5 で PR のタイトル・説明文を生成するときに従う。

## 最優先の原則: diff で分かることは書かない

レビュアーは変更行を読めば「何を・どう変えたか」は分かる。PR 説明文が埋めるべきは、**diff だけでは分からない情報** — なぜこの変更が必要だったのか、選択肢の中から何をなぜ選んだのか、どこを重点的に見てほしいのか。変更内容を逐一なぞる説明（ファイル名・関数名・変数名の羅列）は diff と重複するだけなので書かない。

各文を書くとき「これは diff を見れば分かるか？」と自問する。分かるなら省く。分からないなら書く価値がある。

## スタイル

- 文体は敬体
- 箇条書きで必要十分に。長い散文や変数名・クラス名の羅列は避ける
- 概要は「What（1〜2 文）→ 背景（Why）→ 設計判断（How）→ 影響範囲」の順
- 条件分岐や対応表が要点なら、表に ✅ / ❌ を添えて視覚的に示す
- 情報が無いセクションは丸ごと削る。HTML コメントや過剰な絵文字装飾は残さない

## タイトル

英語で、検索しやすい表現にする。conventional commit 風のプレフィックス（`feat:` / `fix:` など）を推奨。

## テンプレート

情報が無いセクションは削る。説明文が長くなると Bash の承認ダイアログが読みづらくなるため、`gh pr create` には `--body-file` を使う（一旦 `/tmp/pr-body.md` 等に書き出してから渡す）。

```markdown
## 概要

{対応する issue ごとに 1 行: 完了するなら `close #XXXX`、部分対応なら `part of #XXXX`}

{この PR が何を達成するかを 1〜2 文で。変更の羅列ではなく、解決された状態を書く}

### 背景

{なぜこの変更が必要だったか。issue の問題・既存の不都合など、diff からは読み取れない動機を箇条書きで}

### 設計判断

{選択肢があった箇所で何をなぜ選んだか、トレードオフ、実装中に迷った点。diff は「選んだ結果」しか示さないので、その理由を書く}

### 影響範囲

{この変更が波及する箇所、後方互換性、注意が必要な依存。変更行を追うだけでは見えにくい影響を書く}

## 動作確認

### 自動確認済み
- [x] {実行して成功したコマンド}

### 手動確認
- [ ] {自動検証できず人の確認が必要な項目}

---

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

「自動確認済み」「手動確認」は、該当項目が無ければセクションごと省略する。`[x]` は実際に実行して成功したものだけに付ける。

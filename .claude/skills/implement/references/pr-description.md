# PR 説明文の書き方

Step 5 で PR のタイトル・説明文を生成するときに従う。

## 最優先の原則: diff で分かることは書かない

レビュアーは変更行を読めば「何を・どう変えたか」は分かる。PR 説明文が埋めるべきは、**diff だけでは分からない情報** — なぜこの変更が必要だったのか、選択肢の中から何をなぜ選んだのか、どこを重点的に見てほしいのか。変更内容を逐一なぞる説明（ファイル名・関数名・変数名の羅列）は diff と重複するだけなので書かない。

各文を書くとき「これは diff を見れば分かるか？」と自問する。分かるなら省く。分からないなら書く価値がある。

## スタイル

- 文体は敬体
- 箇条書きで必要十分に。長い散文や変数名・クラス名の羅列は避ける
- 条件分岐や対応表が要点なら、表に ✅ / ❌ を添えて視覚的に示す
- 情報が無いセクションは丸ごと削る。ヒントの HTML コメントや過剰な絵文字装飾は残さない

## タイトル

英語で、検索しやすい表現にする。conventional commit 風のプレフィックス（`feat:` / `fix:` など）を推奨。

## 本文の組み立て

本文の骨格（セクション構成）は、リポジトリルートの `.github/PULL_REQUEST_TEMPLATE.md` を正本とする。これを読み、「概要 → 背景 → 設計判断 → 影響範囲 → 動作確認」の各セクションの `<!-- -->` ヒントに従って中身を埋める。ヒントは最終的な body に残さない。情報が無いセクションは削る。

末尾に次のフッターを付ける（テンプレート自体には入っていない。人間が UI から作成したものと区別するため、エージェントが生成するときだけ付ける）。

```
---

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

`gh pr create` には `--body-file` を使う（一旦 `/tmp/pr-body.md` 等に書き出してから渡す）。説明文が長いと Bash の承認ダイアログが読みづらくなるため。

## 動作確認

「自動確認済み」「手動確認」は、該当項目が無ければセクションごと省略する。`[x]` は実際に実行して成功したものだけに付ける（未確認のチェックを確認済みと読み違える事故を防ぐため。Step 4 参照）。
